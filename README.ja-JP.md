GoWind Ops は、Golang フルスタックで実装されたすぐに使えるマルチノード運用プラットフォームです。組織・権限、監査ログ、データ辞書などのシステム機能を標準搭載し、「マシンの管理、プロジェクトの実行、スクリプトの配布、ビルドとデプロイ」に集中できます。

**主な特徴：**

- **4 サービスアーキテクチャ** — core（ドメインリソース層）/ admin / front（BFF）/ agent（エッジプロキシ）の単方向レイヤリング、BFF は DB 非接続
- **MQTT シグナリング長接続** — agent は EMQX への純粋なアウトバウンド接続のみ（インバウンドポートなし）、`$share` 共有サブスクリプションでマルチレプリカ負荷分散、QoS 1 + request_id 冪等性照合
- **大容量ファイルはシグナリングを経由しない** — MinIO プレ署名 URL で直接アップロード/ダウンロード、ストリーミング I/O + SHA-256 検証
- **全コマンドの監査** — すべての命令が台帳に記録（PENDING → 終端ステータス / タイムアウト判定）、実行結果・所要時間・失敗理由を追跡可能
- **ビルド・デプロイ閉ループ** — Git リポジトリ → ビルド（成果物を MinIO へ）→ 対象プロジェクトディレクトリへ配布 / Docker デプロイ → 連動再起動、パイプラインでオーケストレーションし全体をステートマシンで追跡
- **Web ターミナル & ファイルマネージャー** — ブラウザから管理対象マシンのシェルを直接操作（セッション全量監査 + リプレイ）、ファイルの閲覧/編集/一括アップロードはプレ署名 URL で直送
- **オブザーバビリティとガバナンス** — 監視アラート（マルチチャネル通知）、クラウドコスト、証明書台帳、バックアップ、点検、ログスナップショット、操作承認を標準搭載
- **管理フロントエンド** — React 19 + Ant Design 6 + ProComponents、ログイン/権限/監査/辞書を標準搭載

## コア機能

### ノードとプロジェクト

| 機能 | 説明 |
|:------|:----------------------------------------|
| ノード管理 | agent マシンフィンガープリント認可（TOFU 初回接続登録、未認証時自動リトライ）、30 秒ごとのハートビートでメトリクス報告、オンライン状態、名前変更/タグ/環境タグ、CPU/メモリ/ディスク傾向グラフ、ping 命令の送信 |
| プロジェクト管理 | プロジェクト = ノード + ディレクトリ + 起動/停止コマンド；START/STOP/RESTART/STATUS のライフサイクル操作、agent 側の認可ディレクトリ検証（`AGENT_ALLOWED_DIRS`）+ pid ファイル管理；プロジェクト変更タイムライン（配布記録 + アラートの集約） |
| 命令台帳 | すべての命令を監査記録（結果/終了コード/所要時間/失敗理由）、タイムアウトは自動的に FAILED 判定 |
| 実行ログ | プロセス出力を `<プロジェクトdir>/.ops-project.log` に記録；WebSocket リアルタイム tail（差分取得、GBK 保真——Windows コンソールの日本語/中国語が文字化けしない）、ログ末尾の表示とクリア |

### ターミナルとファイル

| 機能 | 説明 |
|:------|:----------------------------------------|
| Web ターミナル | ブラウザから管理対象マシンのシェルを直接操作（xterm.js、WS↔MQTT ブリッジ）；自動再接続/クリップボード/フォント拡大縮小/画面クリア；セッションの入出力を全量監査記録、バイト単位で忠実な読み取り専用リプレイ |
| ファイルマネージャー | ディレクトリツリー + パンくずリスト閲覧、オンライン編集/新規作成/削除、ドラッグ＆ドロップアップロード；マシン選択時にデフォルト作業ディレクトリへ自動移動；大容量ファイルは MinIO プレ署名 URL で直送 |
| バッチコマンド | 複数マシンで同じアドホックコマンドを同時実行、マシンごとのステータス/終了コード/所要時間/出力をリアルタイム表示、結果はバッチ記録に残存 |
| バッチアップロード | 同じファイル群を複数マシンの同一ディレクトリへ配布——ファイルの PUT は 1 回のみ、各対象マシンがそれぞれ取得して保存、アップロード帯域を N-1 倍削減 |

### スクリプトとビルド・デプロイ

| 機能 | 説明 |
|:------|:--------------------------------------------|
| スクリプト管理 | スクリプト CRUD（内容 ≤256KB）、リモート実行：内容は MQTT で配信、一時ファイル経由でプラットフォームのシェルで実行、出力/終了コード/所要時間を台帳に記録、タイムアウト時はプロセスツリーを kill；マルチノード一括実行（バッチ詳細にマシンごとの結果マトリクス） |
| ソースリポジトリ管理 | HTTPS Git / ローカルパス、パスワードは AES-GCM 暗号化保存、表示はマスキング |
| ビルド | ビルド設定 + 非同期トリガー（ビルド番号自動増分、同時実行重複排除、中断判定）、成果物は MinIO `artifacts` バケットへ；ビルドログのリアルタイム tail；成果物バージョン保持ポリシーとロールバック配布 |
| デプロイ | ビルド成果物を対象プロジェクトディレクトリへ配布（zip 展開は zip slip 対策済み、clearOld オプション、配布後の連動再起動/起動）、マルチターゲットは記録ごとにステートマシン追跡；**段階的ロールアウト対応**（1 バッチ N 台、前バッチ全成功で次バッチを投函、1 つでも失敗すれば後続バッチは SKIPPED）；DOCKER デプロイタイプ（イメージタグは `{buildNo}` プレースホルダ対応、agent 側で pull → コンテナ置換 → run -d） |
| ビルドパイプライン | BUILD / SCRIPT / DISTRIBUTION の 3 種類ステップを順序実行、失敗で即中止、未実行ステップは SKIPPED、実行ログの差分 tail |
| 定時タスク | ビルド/スクリプトの cron 式スケジューリング（CAS アンカー重複排除、初回はアンカー設置のみで遡行実行なし） |
| 設定センター | 環境ごとの設定テンプレート、`{{env}}/{{node.*}}/{{project.*}}/{{date}}` プレースホルダをレンダリングして配信、配信記録は終端ステータスで照合 |

## プロジェクト構造

```
go-wind-ops/
├── backend/                        # バックエンドサービス
│   ├── api/                        # Protobuf API 定義 & 生成コード
│   │   ├── protos/                 # .proto ソース（ops 業務ドメイン + ベース継承ドメイン）
│   │   └── gen/                    # 生成コード (Go / TypeScript / OpenAPI)、手動編集禁止
│   ├── app/
│   │   ├── admin/service/          # 管理画面 BFF (REST :18600、gRPC → core、DB 非接続)
│   │   ├── front/service/          # フロント BFF (REST :18700、gRPC → core、DB 非接続)
│   │   ├── core/service/           # ドメインリソース層 (Ent schema/リポジトリ/業務ロジック + MQTT コントロールプレーン + Asynq worker)
│   │   └── agent/service/          # エッジプロキシ (純粋な MQTT アウトバウンド；DB/サービス検索/REST なし)
│   ├── pkg/                        # 共通パッケージ (signal/topic/serviceid/oss/filetransfer/認証ミドルウェア...)
│   └── scripts/                    # デプロイスクリプト (Docker など)
└── frontend/
    └── admin/                      # 管理フロントエンド (React 19 + Ant Design 6 + ProComponents + Vite 6)
```

## クイックスタート

### 前提条件

- Go 1.26+
- Docker & Docker Compose
- Node.js 20+ & pnpm
- buf / protoc ツールチェーン（proto 変更時のみ必要、`cd backend && make init` で一括インストール）

### 1. 依存サービスの起動

```bash
cd backend
docker compose -f docker-compose.libs.yaml up -d   # PG/Redis/MinIO/etcd/EMQX/Jaeger
```

### 2. バックエンドサービスの起動

```bash
cd backend
go build -o bin/core ./app/core/service/cmd/server && ./bin/core -c app/core/service/configs
go build -o bin/agent ./app/agent/service/cmd/server && ./bin/agent -c app/agent/service/configs
```

agent は初回起動時に作業ディレクトリへ `auth.token` を生成し、MQTT 経由で core に登録します（TOFU、認証されるまで 5 秒ごとにリトライ）、その後 30 秒ごとにハートビートでメトリクスを報告します。管理対象マシンで agent を実行する前に、認可ディレクトリ（環境変数 `AGENT_ALLOWED_DIRS`、プラットフォームのパスリスト区切り文字で区切り）を設定してください。プロジェクトディレクトリが認可ディレクトリ内にない場合、agent は実行を拒否します。

### 3. 管理フロントエンドの起動

```bash
cd frontend/admin
pnpm install
pnpm dev        # http://localhost:18999、/admin → 127.0.0.1:18600 へプロキシ
```

デフォルトアカウントは `admin / admin`（開発環境では `ADMIN_CAPTCHA_DISABLED=true` で認証コードをスキップ可能；ログインパスワードはフロントエンドの規約に従い AES-GCM で暗号化する必要があります。`backend/tools/pass-enc` を参照）。

### よく使うコマンド

```bash
cd backend

# Ent ORM コードの生成
make ent

# Protobuf API Go コードの生成
make api

# 管理フロントエンド TypeScript クライアントの生成
cd api && buf generate --template buf.admin.typescript.gen.yaml

# 全コードの一括生成 (ent + api + openapi)
make gen

# 全サービスのビルド
make build

# テストの実行
make test
```

> 管理側 REST インターフェースの一覧（ノード/プロジェクト/スクリプト/リポジトリ/ビルド/デプロイ/台帳の全エンドポイント）は [backend/README.md](./backend/README.md)、バックエンドの開発規約とアーキテクチャの詳細は [backend/AGENTS.md](./backend/AGENTS.md) を参照してください。
